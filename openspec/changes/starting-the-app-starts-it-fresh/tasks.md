## 1. The clock cannot report time from before it existed

- [x] 1.1 `IdleClock` -- capture the origin from the `now` handed to the first `Elapsed` call,
      first value winning, so the class still reads no clock of its own.
- [x] 1.2 Bound the returned value by the time since that origin, applied *after* the hold-off
      subtraction rather than to `systemIdle` before it.
- [x] 1.3 Rewrite the class summary: it corrects the system counter twice now, for the same
      reason both times, and the second correction should not read as an afterthought.
- [x] 1.4 Confirm nothing else reads `NativeInput.IdleSeconds()` directly and bypasses this.

## 2. Tests for the clock

- [x] 2.1 A clock whose first tick reports a large system idle returns nearly zero.
- [x] 2.2 It reaches `IdleSeconds` only after that much time has actually passed since the run
      began, not before.
- [x] 2.3 Once the run is older than the system idle, the bound stops applying and the reported
      value is the system idle again.
- [x] 2.4 The hold-off discount still behaves exactly as it did -- run the existing scenarios
      past the point where the bound is no longer in play, so the new ceiling is proved not to
      have quietly replaced the subtraction.
- [x] 2.5 Input arriving does not move the origin: the bound goes on being measured from the
      start of the run.

## 3. The application can be found

- [x] 3.1 `Startup` -- write a per-user Start Menu `.lnk` pointing at `Environment.ProcessPath`

      swallow-everything envelope.
- [x] 3.2 Delete it wherever the `Run` value is deleted, so nothing is left behind.
- [x] 3.3 Leave `IsEnabled` reading the `Run` key alone -- a missing shortcut must not make the

the deliverable.
